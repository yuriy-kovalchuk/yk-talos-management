# Features

Complete reference for all controller capabilities with examples.

---

## Machine Config Apply

The controller applies Talos machine configs to nodes using the Talos API. It automatically selects the right transport:

- **First apply** — node is in maintenance mode with a self-signed cert. The controller uses `InsecureSkipVerify` (`DialInsecure`).
- **Subsequent applies** — mTLS using the talosconfig generated by `TalosCluster`.

Apply is idempotent: `observedGeneration == generation && ConfigApplied == True` → skip.

### Config apply mode

The Talos API responds with the apply mode it used: `NO_REBOOT`, `REBOOT`, or `STAGED`. The controller logs this and records it in the `talos_config_apply_mode_total` metric.

## Per-Node Patches

Apply YAML patches on top of the base `controlplane.yaml` or `worker.yaml`. Two patch formats are supported:

**Deep merge** (no `apiVersion` key) — recursively merges into the base config. Use for overriding `machine:` or `cluster:` fields:

```yaml
spec:
  patches:
    - |
      machine:
        network:
          hostname: prod-cp1
          nameservers:
            - 1.1.1.1
    - |
      machine:
        kubelet:
          extraArgs:
            max-pods: "200"
```

**Standalone document** (has `apiVersion`) — appended as a separate YAML document. Use for Talos extension configs:

```yaml
spec:
  patches:
    - |
      apiVersion: v1alpha1
      kind: RegistryMirrorConfig
      mirrors:
        docker.io:
          endpoints:
            - https://mirror.example.com
```

**Secret-backed patches** — for sensitive values (credentials, keys) that should not be inlined in the manifest:

```yaml
spec:
  patchesFrom:
    - name: node-registry-creds
      key: patch.yaml
```

Inline `patches` are applied first, then `patchesFrom` patches. The final merged config is stored in `{node}-config` Secret for drift detection.

## Drift Detection

The controller periodically fetches the running machine config from each node via the Talos COSI resource API and compares it with the desired config stored in `{node}-config` Secret.

- **Interval:** 5 minutes
- **Comparison:** semantic (YAML parse + `reflect.DeepEqual`). Whitespace and comment differences are ignored.
- **On drift:** re-applies the desired config automatically and emits a `DriftDetected` warning event.
- **Node unreachable:** silently skipped; no event, no error. The next check fires 5 minutes later.

Drift detection is **opt-out**. Disable for nodes that are frequently offline:

```yaml
spec:
  driftDetection: false
```

## Talos Version Upgrade

Two paths exist to upgrade the Talos OS on a node. Both reuse the same upgrade engine (`handleUpgrade`) and result in the same `Upgrading` → `Ready` lifecycle.

### Declarative (spec.talosVersion)

Set the desired OS version in the `TalosNode` spec. The controller upgrades automatically when `spec.talosVersion != status.currentTalosVersion`:

```yaml
spec:
  talosVersion: v1.13.2
```

To upgrade a full cluster, update `spec.talosVersion` on every node (and `TalosCluster.spec.talosVersion` for config schema consistency). Nodes upgrade independently and concurrently.

### Imperative (annotation)

Use the upgrade annotation as an escape hatch or for one-off upgrades:

```bash
kubectl annotate talosnode prod-cp1 \
  talos.yuriykovalchuk.dev/upgrade=ghcr.io/siderolabs/installer:v1.13.2
```

The annotation takes priority over `spec.talosVersion` for that reconcile. The companion `last-upgrade` annotation is set when the RPC completes (success or failure) to prevent re-triggering.

### Upgrade lifecycle

```
Ready
  │  upgrade triggered (annotation or spec change)
  ▼
Upgrading ──── polling every 30s ─────────────────┐
  │                                                │ node offline (rebooting)
  │  node online, version matches expected         │
  ▼                                                │
Ready ◄──────────────────────────────────────────-┘
  status.currentTalosVersion = new version
  TalosVersionUpToDate condition = True
```

### Protections

- **Downgrade blocked.** Attempts to downgrade are rejected with a `DowngradeBlocked` warning event. The trigger is consumed so the event fires once, not on every reconcile.
- **Container (Docker) mode.** Upgrades are a no-op on Talos container nodes. The controller emits `UpgradeSkipped` and does not consume the trigger.
- **Version normalisation.** `"1.13.2"` and `"v1.13.2"` are treated identically; the `v` prefix is added if missing.

## System Extensions (Image Factory)

Talos system extensions are baked into the boot image — they cannot be installed at runtime. When `spec.systemExtensions` is set, the controller calls the [Talos Image Factory](https://factory.talos.dev) to build a custom installer image and upgrades the node to it.

```yaml
spec:
  talosVersion: v1.13.2
  systemExtensions:
    - siderolabs/iscsi-tools
    - siderolabs/util-linux-tools
```

Extension changes (add, remove, reorder) trigger an automatic upgrade to the new factory image. Nodes in the same cluster can have different extension sets.

### How the factory integration works

1. The controller computes a canonical extension string (sorted, joined) and compares it against the `last-extensions` annotation.
2. **Cache hit** (extension list unchanged): uses the schematic ID from the `current-schematic` annotation. No HTTP call.
3. **Cache miss** (extension list changed): calls `POST factory.talos.dev/schematics` → receives a schematic ID → constructs `factory.talos.dev/installer/<id>:<version>`.
4. Schematic ID and canonical extension string are persisted in annotations before the upgrade RPC is sent, so a controller restart cannot cause a double-call.

### Status after upgrade

```yaml
status:
  currentTalosVersion: v1.13.2
  installedExtensions:
    - siderolabs/iscsi-tools
    - siderolabs/util-linux-tools
  conditions:
    - type: ExtensionsUpToDate
      status: "True"
```

### Combining version upgrade and extension change

Setting both `spec.talosVersion` and `spec.systemExtensions` in the same commit results in a **single reboot** that applies both changes. The factory is called once for the new schematic, and the upgrade image carries the new version and the new extension set.

## Node Removal

Deleting a `TalosNode` triggers a fully managed teardown sequence. All steps are guarded by a finalizer.

### Worker sequence

```
Cordon → Drain pods → Delete k8s Node object → Delete {node}-config Secret → Remove finalizer
```

### ControlPlane sequence

```
Cordon → Drain pods → Delete k8s Node object
  → EtcdLeave (up to 3 × 90s)
  → EtcdForceRemove via surviving peer (if graceful leave fails)
  → [Reset if spec.resetOnDelete=true]
  → Delete {node}-config Secret
  → Remove nodeIP from TalosCluster.spec.endpoints
  → Remove finalizer
```

Removing the IP from `TalosCluster.spec.endpoints` triggers a re-reconcile that regenerates machine configs without the dead endpoint.

### Drain

The drain step resolves the node hostname via the Talos COSI API (`talosctl get hostname`) before cordoning. This ensures the k8s `Node` object is found by name regardless of which interface kubelet registered with.

If the dial fails (node offline), drain is silently skipped and deletion continues.

### Spec fields for removal

| Field | Default | Description |
|-------|---------|-------------|
| `skipDrain` | `false` | Skip cordon and pod eviction |
| `drainTimeout` | `5m` | Max time to wait for pod eviction |
| `resetOnDelete` | `false` | Wipe the node and reboot to maintenance mode after etcd leave. Best-effort. **No-op on Docker nodes** |

### Annotation escape hatch

Bypass drain on an already-terminating object without patching the spec:

```bash
kubectl annotate talosnode prod-cp1 \
  talos.yuriykovalchuk.dev/skip-drain=true
```

### Last ControlPlane guard

Deleting the last active ControlPlane is **blocked** — the controller requeues every 30s. Add a replacement CP first, or delete the entire cluster in order (nodes → bootstrap → cluster).

### Cluster teardown order

```bash
kubectl delete talosnode --all -n <namespace>
kubectl delete talosclusterbootstrap <name> -n <namespace>
kubectl delete taloscluster <name> -n <namespace>
```

## Standalone Node Reset

Wipe a node and reboot it to maintenance mode **without removing it from the cluster**. The controller re-applies the machine config automatically after the node comes back up.

```bash
kubectl annotate talosnode prod-cp1 \
  talos.yuriykovalchuk.dev/reset=$(date +%s)
```

Use a unique value each time (timestamp, UUID). The companion `last-reset` annotation is set before the Reset RPC so a controller crash cannot cause a loop. ArgoCD/Flux restoring the same annotation value is a no-op.

> **Docker nodes:** the reset call shuts the container down but does not wipe data. Use `make talos-down` + `make talos-up` instead.

Events:

| Event | Reason |
|-------|--------|
| Normal | `NodeResetTriggered` |
| Normal | `NodeResetComplete` |
| Warning | `NodeResetFailed` |

## Kubernetes Version Pinning

By default, `TalosCluster` uses the Kubernetes version bundled with the Talos SDK for the given `talosVersion`. Override it with `spec.kubernetesVersion`:

```yaml
spec:
  talosVersion: v1.13.2
  kubernetesVersion: "1.32.3"
```

Changing `kubernetesVersion` regenerates `controlplane.yaml` and `worker.yaml`. Drift detection then re-applies the new config to each node, which triggers the Kubernetes component upgrade on next reconcile.

> `TalosCluster.spec.talosVersion` and `spec.kubernetesVersion` control **config generation** only. They do not upgrade the Talos OS running on any node — that requires `TalosNode.spec.talosVersion`.

## GitOps Compatibility

All one-shot operations use companion annotations as idempotency keys so that GitOps tools (ArgoCD, Flux) restoring the trigger annotation never cause loops.

| Trigger annotation | Companion | Idempotency condition |
|---|---|---|
| `upgrade` | `last-upgrade` | Skip when `upgrade == last-upgrade` |
| `reset` | `last-reset` | Skip when `reset == last-reset` |

To re-trigger, change the annotation value.

## Prometheus Metrics

The operator exposes Prometheus metrics at `:8080/metrics`. A Grafana dashboard is provided in `config/manager/grafana-dashboard.yaml` and is auto-loaded by the Grafana sidecar (label `grafana_dashboard=1`).

Key metrics:

| Metric | Description |
|--------|-------------|
| `talos_node_phase` | Active phase per node (gauge, 1 = current) |
| `talos_cluster_phase` | Active phase per cluster |
| `talos_bootstrap_phase` | Active phase per bootstrap |
| `talos_config_apply_total` | Config apply attempts by role and result |
| `talos_drift_check_total` | Drift check outcomes: `in_sync`, `drifted`, `unreachable`, `error` |
| `talos_node_upgrade_total` | Upgrade outcomes: `success`, `error`, `skipped`, `blocked` |
| `talos_extension_schematic_total` | Factory calls: `success`, `error`, `cached` |
| `talos_etcd_leave_total` | EtcdLeave outcomes during CP removal |
| `talos_api_call_duration_seconds` | Talos gRPC call latency by operation |

Install the monitoring stack for local development:

```bash
make monitoring-up
make monitoring-forward
# Grafana → http://localhost:3000 (admin/admin)
```
